### Folder Structure: Category Based, Not Island Based

So I had two choices before writing any data acquisition code. Could organize by island (meaning a separate Maldives folder, a Seychelles folder, with each place holding all its own data files), or I could organize strictly by data category (a settlements folder, a mangroves folder, with each holding all five islands' files together). 

Chose the category based plan. (The main reason was my analysis methodology, because I need to compare the exact same variable across all five islands at once—like coral bleaching stress or encroachment rates—so an island based structure woudl mean opening five separate folders every single time a cross island script runs). It becomes a huge headache. Also, people easily make inconsistent naming mistakes when files are hidden inside separate island folders. Category based keeps every version of a dataset right in one place. My cross island script just runs a simple loop over the island names reading from tht single folder. (It is immediately obvious if any island's file is missing from a category because all five files should be sitting right nxt to each other in the directory). This layout keeps my data clean.

The top level structure ended up as:

```
DOUBLE_JEOPARDY/
├── data/
│   ├── settlements/
│   ├── ecosystem_buffers/       (mangroves, coral reefs, protected areas)
│   ├── terrain/                 (elevation, slope)
│   ├── population/
│   ├── cyclone_tracks/
│   ├── boundaries/               (island outlines)
│   ├── mangroves/                (raw multi-temporal GMW archives, kept separate from processed ecosystem_buffers)
│   ├── coral_bleaching/          (NOAA thermal stress time series)
│   └── settlement_encroachment/  (satellite-derived built-up change data)
├── outputs/
│   └── plots/
├── DJ_Research_Paper.md
├── DJ_Executive_Summary.md
└── DJ_Development_Log.md
```

So I made one deliberate inconsistency in my folder setup............ (The raw multi temporal Global Mangrove Watch archives for the 1996, 2010, n 2020 snapshots live inside their own mangroves/ folder, which is completely separate from the clean per island files inside the ecosystem_buffers/ directory). Chose this for practical reasons. The raw GMW shapefiles are absolutely massive since they weigh around 900 to 950 megabytes per year n cover the whole globe. Only need to process them once into tiny per island n per year extracts. (By keeping the giant source archives physically away from the small final files, I easily excluded the heavy raw archives from my Git version control while still tracking the lightweight output files nicely). This saved me from scattering folder level exceptions everywhere......

### Environment Setup

I reused my old gpie2 conda environment. (I did not want to start fresh because this specific environment was already fixed for a nasty numerical computing issue where a corrupted Intel MKL backend was breaking my scripts). So I solved tht old error by installing NumPy and SciPy with the nomkl OpenBLAS backend instead. Reusing it meant I did not risk facing tht same failure mode again in a clean environment. ### Why This Mattered Later

My upfront folder structure paid off beautifully. (Once I started the multi temporal analysis, everything became super easy because every mangrove year file, every coral time series file, nd every island's settlement file sat in a totally predictable, category consistent spot in my directory layout). This choice saved me hours of extra coding later....... My scripts looping across all five islands—like the elevation exposure checks, mangrove area comparisons, nd coral stress trends—could be written in a generic way. (Only had to change the island name between iterations instead of writing five near duplicate scripts hardcoded to five completely different folder setups). This trick kept my development log clean.

### Source and Acquisition

I grabbed all three datasets from OpenStreetMap. (So I ran specific Overpass Turbo queries filtered exactly to each island's borders, which gave me one raw GeoJSON export per island for each distinct category to create fifteen total files). So I chose OSM because it was practical. It gives me consistent, free data across five different national administrative systems—Maldives, India, Seychelles, Fiji, n Spain. (No single government office provides a dataset tht covers all five islands in the same format, so I had to use OSM to keep my framework uniform).............. This solved a huge matching problem.

### The Column Bloat Problem

My raw OSM exports had an absurd number of columns. (Usually, I found around 200 to 240 columns in every single file, but most of it was total garbage like place name translations into dozens of languages such as name:ta, name:zh Latn pinyin, or wikipedia:ur, along with Wikidata links and contact info tht had nothing to do with settlement identity, population, or location). I did not want to carry this dead weight around. It made checking files by hand a massive headache. 

So, I chose to clean all fifteen files the exact same way. Read them into my script using geopandas nd trimmed down the data to columns that actually mattered....... (For settlements, I kept name, place type, population, nd geometry; for tourism, I chose name, tourism type, amenity type, and geometry; n for infrastructure, I saved name, man made feature type, amenity type, power infrastructure type, nd geometry). Then I saved them as new _clean.gpkg files. (So I left my original raw GeoJSON files untouched so I did not lose any source data). My settlement files dropped from 240 columns down to jst 4 or 5. I did not lose a single row or any useful field during this process.

### Bug: Sea Features Mislabeled as Settlements

So I found a weird bug while checking my clean settlement files. (My bounding boxes for the Maldives nd Lakshadweep data looked way too massive nd extended way outside the actual island borders). Two specific rows caused this mess in both files. They were labeled "Arabian Sea" n "Laccadive Sea." (These entries were obviously not real human settlements at all, but random OSM features for large water bodies that got accidentally dragged into my Overpass Turbo place type query because online contributors tag things inconsistently). It happens a lot on OSM.

Caught this mistake by doing a quick trick. Calculated the centroid coordinates for every single settlement, sorted everything by longitude, n checked the extreme values at both ends. (The two sea name rows stuck out like a sore thumb immediately because their coordinates were sitting far away from the actual settlement clusters). So, I chose to delete both rows directly from my cleaned .gpkg files. (My Maldives file dropped from 998 to 996 rows, nd my Lakshadweep data went from 38 down to 36 rows). This fixed the bug completely without making me re pull anything from OpenStreetMap.

### Bug: Invalid Geometry in Tourism Data

I hit a major code crash. (While I was trying to read the Canary Islands tourism dataset, geopandas.read_file() suddenly threw a bad GEOSException error about an invalid number of points in a LinearRing). The file only had 2 points instead of the 4 pairs needed to make a proper loop. This is a realy common mistake. (People who edit crowd sourced OpenStreetMap data frequently make these broken, half finished polygon lines by mistake). 

So I fixed the crash easily. I chose to pass on_invalid="ignore" right inside the geopandas.read_file() command so my script drops unreadable geometries instead of dying. Then I ran an explicit check. (I wanted to count if there were any null geometries left after the read, and I found exactly two invalid rows in the Canary tourism file). My rows dropped from 10,877 down to 10,875 valid ones. Made this exact setup a standard step for all my later vector cleaning scripts. (Broken polygon defects can show up anywhere when u use open source OSM files, so adding this check keeps my pipeline safe). This saved my code from breaking again.

### Duplicate and Naming Cleanup

I found a few naming inconsistencies here. (This issue became a recurring pattern throughout my whole project becuase manually re running exports keeps producing near duplicate files under slightly different names). So I had to double check everything. Fiji's protected area adjacent file existed twice in my directory as FIJI_INFRAA_SLR.gpkg with a silly typo extra "A" n as the clean FIJI_INFRA_SLR.gpkg version. They were identical in size. (Chose to delete the typo'd copy directly from my folder to save space). I used this same handling pattern every single time this issue popped up anywhere else. So I always checked the file sizes or row counts 1st to confirm whether the copies actually differ. (Then I deleted the confirmed duplicates immediately rather than leaving ambiguous near identical files sitting around making my folders look messy). This kept my directory clean.

### Terrain: Elevation nd Slope

I got my elevation data from Copernicus DEM. (Luckily, the files for all five islands arrived in the correct EPSG:4326 coordinate system right from the start, so I did not have to waste time doing any map re projections there). That was an easy win.

(I had to fix this by writing a script with rasterio's calculate_default_transform n reproject functions using bilinear resampling because tht is the correct way to handle smooth continuous elevation stuff instead of nearest neighbor resampling which is only for category grids like land cover). Seychelles was even worse because it had zero slope files in the folder. (Instead of crying or downloading new files, I chose to generate the slope layer directly from my already checked Seychelles elevation raster using GDAL's gdaldem slope command in my terminal). This gave me a perfectly matching slope raster without downloading any extra junk. It saved my day.

So I cross checked elevation values manually. (Matched my raster data against real geography maps as a sanity check because I did not want to jst blindly trust random numbers on my screen). My Canary Islands file maxed out at around 3,696 meters. (This lines up nicely with Mount Teide, which is Spain's highest peak sitting at roughly 3,715 meters). The Seychelles data hit a top peak of around 904 meters. (This fits its steep granite mountain geography like Morne Seychellois perfectly). On the other hand, the Maldives and Lakshadweep layers stayed strictly in a super low 0 to 20 meters range. (This matches exactly wht you expect for low lying coral atoll nations on any map). This quick matching test gave me high confidence. My height layers were processed correctly and did not get silently corrupted or shifted.

### Population: Checked Against Real Numbers

This trick saved my system memory. Phew.

### Cyclone Tracks: IBTrACS n a Wind Speed Consolidation Problem

I got historical cyclone track data from IBTrACS. (This is NOAA's standard global cyclone dataset that mixes reports from more than a dozen different meteorological offices). It was a very big file. I chose to filter down the full global shapefile per island using the exact same bounding box geopandas.read_file(bbox=...) approach tht I already used for my WDPA files. This method saved my computer from crashing.
